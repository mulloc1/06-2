# AI Git CLI 재구현 계획

이 문서는 `subject.md`의 필수 요구사항과 `평가문항.md`의 16개 평가 기준만을 기준으로 작성한 재구현 계획이다. 기존 구현을 전제로 하지 않으며, 필수 기능을 먼저 완성한 뒤 선택 과제를 별도 확장한다.

## 1. 목표와 완료 조건

프로젝트 루트에서 실행하는 Python CLI를 만든다. CLI는 Git 변경 파일과 diff를 수집해 AI API에 전달하고 다음 결과를 터미널에 출력한다.

- `commit`: 출력용 라벨이나 본문 없이 한 줄로 구성된 커밋 메시지 초안
- `pr`: 한 줄 제목과 `Why`, `What`, `How to Test` 섹션이 있는 PR 초안
- 코디세이 virtual key는 `CODYSSEY_API_KEY` 환경변수로만 읽고, 모델·temperature·max tokens는 CLI 옵션으로 조정
- 변경사항 없음, 인증 실패, HTTP 401/429, 네트워크 오류, 타임아웃을 구분해 안내
- 생성 결과를 검증·보정하되 항상 사용자의 수동 검토가 필요하다고 명시
- README만으로 설치, 설정, 실행, 결과 확인이 가능

완료 시에는 단위 테스트와 명령 단위 통합 테스트가 통과하고, 실제 Git 저장소에서 두 명령의 end-to-end 실행 결과를 확인한다. GitHub 저장소 생성과 push는 로컬 기능 검증 후 마지막 단계에서 수행한다.

## 2. 범위

### 필수 범위

1. Git 저장소 및 프로젝트 루트 확인
2. `git status --short`, staged/unstaged diff, 신규 파일 정보 수집
3. AI REST API 요청·응답 처리
4. 커밋 메시지와 PR 초안 생성
5. 형식·길이 검증 및 제한된 재생성
6. 원인별 오류 처리와 종료 코드
7. API 파라미터 CLI 옵션
8. 테스트, README, 실제 실행 검증, GitHub push

### 선택 범위

핵심 완료 후에만 팀 규칙 파일, 사용자 정의 템플릿, 고급 safe mode, 실제 PR 생성 과제를 진행한다. 선택 기능 때문에 필수 기능의 구조나 일정이 복잡해지지 않도록 별도 단계로 격리한다.

## 3. 설계 원칙

### 책임 분리

| 영역 | 책임 | 테스트 방식 |
| --- | --- | --- |
| CLI | 인자 파싱, 실행 흐름, 출력 | 명령 흐름 테스트 |
| Git 수집 | 저장소 확인, status/diff 실행, 변경 스냅샷 생성 | 임시 Git 저장소 |
| AI 클라이언트 | 환경변수, HTTP 요청, 응답 파싱, 오류 분류 | HTTP 계층 mock/fake |
| 프롬프트 | 변경 파일과 diff를 목적별 형식 지시와 결합 | 순수 문자열 단위 테스트 |
| 검증 | 길이, 제목, 섹션, 불릿 검사 | 테이블 기반 단위 테스트 |

Git subprocess와 HTTP 호출을 분리하면 네트워크 없이 대부분의 동작을 검증할 수 있고, AI 제공자를 바꿔도 Git 수집과 출력 규칙에 영향이 없다.

### 프롬프트와 검증의 역할

- 프롬프트는 모델이 처음부터 올바른 형식을 만들도록 변경 파일, diff, 제목 제한, 본문 템플릿을 명시한다.
- 검증은 제목 길이, 필수 헤더, 불릿 존재 여부처럼 기계적으로 판정 가능한 규칙만 담당한다.
- 내용이 누락되거나 근거 없는 경우에는 문자열을 억지로 만들어 넣지 않고 한 번 재생성한다.
- 유효한 AI 원문은 재조립하지 않고 그대로 출력한다.
- 재생성 후에도 실패하면 오류로 종료하며 정상 초안으로 위장하지 않는다.

이 방식은 출력 품질과 비용을 균형 있게 관리하고, 재생성과 검증의 선택 근거를 설명할 수 있게 한다.

### AI 파라미터

- `--model`: 모델 교체 및 비용·품질 비교
- `--temperature`: 기본값은 낮게 두어 형식과 재현성을 우선하며, 아이디어 다양성이 필요할 때만 높임
- `--max-tokens`: 출력 상한과 비용을 제어하되 너무 작을 때 PR 본문이 절단될 수 있음을 검증
- `--timeout`: 네트워크 대기 상한을 명시해 멈춤을 방지

기본값은 한 곳에서 관리하고 `--help`와 README에 동일하게 표시한다. 값의 유효 범위도 CLI 진입점에서 검사한다.

### 코디세이 API 계약

- OpenAI 호환 Base URL: `https://copa.codyssey.kr/v1`
- 채팅 Endpoint: `POST /chat/completions`
- 인증: `Authorization: Bearer <virtual-key>`
- 기본 모델: `gpt-5-mini`
- 환경변수: `CODYSSEY_API_KEY`

API 콘솔에 표시된 계약을 코드 상수와 README에 동일하게 반영하며, 키 값은 저장소에 기록하지 않는다.

## 4. 제안 구조

구현 시 다음과 같은 최소 구조를 사용한다. 실제 파일명은 구현 시작 시 테스트 편의성을 해치지 않는 범위에서 조정할 수 있다.

```text
src/ai_git_cli/
├── __init__.py
├── __main__.py       # python -m ai_git_cli
├── cli.py            # argparse와 실행 흐름
├── git_changes.py    # Git 수집
├── ai_client.py      # REST API 및 오류 분류
├── prompts.py        # commit/pr 프롬프트
└── validators.py     # 출력 형식 검증

tests/
├── test_cli.py
├── test_git_changes.py
├── test_ai_client.py
├── test_prompts.py
└── test_validators.py
```

현재 남아 있는 테스트는 이전 구현의 계약을 담고 있을 수 있다. 새 구현을 시작할 때 각 테스트를 새 요구사항과 대조해 재사용, 수정, 삭제 여부를 결정하며, 삭제만 해서 테스트를 통과시키지 않는다.

## 5. 명령 및 출력 계약

### 명령

```bash
python -m ai_git_cli commit [공통 옵션]
python -m ai_git_cli pr [공통 옵션]
```

공통 옵션은 최소 `--model`, `--temperature`, `--max-tokens`, `--timeout`을 제공한다. 옵션은 서브커맨드 앞이나 뒤 중 한 위치로 일관되게 정하고 README 예시와 테스트에서 고정한다.

### 변경사항 없음

변경사항이 없으면 AI API를 호출하지 않고 `변경사항이 없습니다.`와 같은 명시적 메시지를 stdout에 출력한 뒤 종료 코드 0으로 끝낸다.

### 커밋 초안

- 초안임을 나타내는 헤더
- 출력용 라벨이나 본문 없이 한 줄: 권장 50자 이하, 절대 최대 72자
- 사용 전 검토·수정하라는 안내

### PR 초안

- 초안임을 나타내는 헤더와 한 줄 제목
- 제목 최대 80자
- `## Why`, `## What`, `## How to Test` 헤더
- 각 섹션에 최소 한 개의 불릿
- 사용 전 사실관계와 테스트 절차를 검토하라는 안내

## 6. 오류 계약

사용자 메시지에는 실패 종류와 원인을 함께 표시하고 API 키 값이나 Authorization 헤더는 절대 출력하지 않는다.

| 상황 | 기대 동작 |
| --- | --- |
| API 키 누락 | 환경변수 이름과 설정 방법을 포함한 오류 |
| HTTP 401 | 인증 실패로 분류하고 키·권한 확인 안내 |
| HTTP 429 | rate limit/할당량 실패로 분류하고 재시도·사용량 확인 안내 |
| 기타 HTTP 오류 | 상태 코드와 안전하게 정리한 응답 원인 |
| 네트워크 오류 | 연결 실패 원인 표시 |
| 타임아웃 | 제한 시간을 포함한 타임아웃 안내 |
| Git 저장소 아님 | 저장소 루트에서 실행하라는 안내 |
| Git 명령 실패 | 실패한 작업과 stderr 원인 표시 |

종료 코드는 성공 `0`, 실행 오류 `1`, 사용법 오류 `2`로 단순화하고 테스트와 README에서 동일하게 사용한다.

## 7. 단계별 실행 계획

### 0단계 — 기준선 정리와 테스트 계약

- `pyproject.toml`, 기존 테스트, README를 새 요구사항과 대조한다.
- 패키지명, Python 최소 버전, 실행 명령, API 키 환경변수, 종료 코드를 확정한다.
- 기존 테스트 중 요구사항과 맞는 시나리오는 보존하고, 구현 세부사항에 결합된 테스트는 행동 중심으로 다시 작성한다.

검증: CLI help 스냅샷과 요구사항-테스트 추적표가 존재해야 한다.

### 1단계 — CLI 뼈대와 Git 변경 수집

- `commit`, `pr` 서브커맨드와 공통 옵션을 구현한다.
- 현재 위치가 Git 저장소 루트인지 검사한다.
- status, staged diff, unstaged diff를 수집하고 변경 파일 목록을 정규화한다.
- 신규 untracked 파일은 status와 파일 목록에만 포함하고 내용은 전송하지 않는다.
- 변경사항 없음 경로에서는 API 호출 전에 정상 종료한다.

검증: 깨끗한 저장소, staged만 있는 경우, unstaged만 있는 경우, 둘 다 있는 경우, untracked 파일, 비-Git 디렉터리를 임시 저장소 테스트로 확인한다.

### 2단계 — AI REST 클라이언트와 오류 처리

- 환경변수에서 API 키를 읽고 요청 헤더에만 사용한다.
- 모델, temperature, max tokens, timeout을 요청 값에 반영한다.
- 응답 스키마를 검증하고 텍스트를 추출한다.
- 단일 API 오류를 사용하되 401, 429, 기타 HTTP, 연결 실패, 타임아웃, 잘못된 응답을 메시지로 구분한다.

검증: 실제 네트워크를 쓰지 않는 fake/mocked 응답으로 성공과 모든 오류 분기를 테스트하며, 로그·오류에 비밀 값이 노출되지 않는지 검사한다.

### 3단계 — 목적별 프롬프트

- 공통 컨텍스트에 변경 파일 목록과 diff를 포함한다.
- 커밋 프롬프트에 한 줄 제목, 길이 제한, 선택 본문 규칙을 명시한다.
- PR 프롬프트에 제목 제한과 세 필수 섹션·불릿 형식을 정확히 명시한다.
- diff에 없는 동작, 파일, 테스트 결과를 추측하지 말라고 지시한다.

검증: 두 프롬프트에 파일 목록, diff, 각 출력 규칙이 포함되는지 단위 테스트한다.

### 4단계 — 검증과 재생성 정책

- 커밋 제목과 PR 제목을 파싱하고 글자 수를 검사한다.
- PR 세 섹션과 각 불릿을 검증한다.
- 유효한 원문은 수정하지 않고 그대로 출력한다.
- 재생성은 최대 한 번으로 제한하고 실패 이유를 보정 프롬프트에 포함한다.
- 최종 결과가 규칙을 위반하면 경고 또는 실패로 처리하며 조작된 성공 결과를 만들지 않는다.

검증: 경계값 50/51/72/73자, PR 제목 80/81자, 누락 헤더, 빈 섹션, 잘못된 불릿, 재생성 성공/실패를 모두 테스트한다.

### 5단계 — 통합 흐름과 터미널 출력

- Git 수집 → 프롬프트 → API → 검증/재생성 → 출력 흐름을 연결한다.
- stdout에는 복사 가능한 초안을, stderr에는 오류·경고를 출력한다.
- 커밋/PR 모두 초안 표시, 명확한 구분선, 수동 검토 안내를 제공한다.
- CLI 옵션이 실제 API 요청에 전달되는지 통합 테스트한다.

검증: fake AI 클라이언트를 사용해 API 키 누락, 변경 없음, 커밋 성공, PR 성공, 포맷 재생성, 원인별 실패 시나리오를 명령 단위로 확인한다.

### 6단계 — README와 운영 안내

- 설치, 환경변수 설정, 두 명령과 옵션, 샘플 출력, 종료 코드를 문서화한다.
- temperature와 max tokens가 품질·무작위성·길이·절단 위험에 미치는 영향을 설명한다.
- 비용과 rate limit, diff 외부 전송, 비밀정보 보호, AI 오류·편향, 수동 검토 필요성을 안내한다.
- README 명령을 깨끗한 환경에서 그대로 실행해 문서만으로 재현되는지 확인한다.

검증: README 예시와 실제 `--help`, 기본값, 출력 형식이 일치해야 한다.

### 7단계 — 최종 검증과 GitHub 전달

- 전체 테스트를 실행하고 실패가 없는지 확인한다.
- 실제 Git 변경을 만들어 `commit`과 `pr`을 각각 한 번 end-to-end 실행한다.
- API 키가 저장소, 로그, 샘플 출력, Git 이력에 없는지 검색한다.
- GitHub 저장소를 생성·push하고 코드, 브랜치, 커밋, README가 열람 가능한지 확인한다.

검증: 새 clone에서 설치 → 환경변수 → 두 명령 실행 흐름이 성공해야 한다.

## 10. 주요 위험과 대응

- 큰 diff로 비용·컨텍스트가 증가할 수 있음을 사용자에게 안내한다.
- untracked 파일은 일반 diff에 나타나지 않으므로 status와 파일명만 보내고 내용은 전송하지 않는다.
- AI가 존재하지 않는 변경이나 테스트 결과를 만들 수 있으므로 프롬프트 억제, 구조 검증, 수동 검토 안내를 함께 사용한다.
- 자동 수정이 의미를 바꿀 수 있으므로 내용 보완은 한 번의 재생성 또는 사용자 검토로 넘긴다.
- 실제 API 테스트는 비용·네트워크에 의존하므로 자동 테스트는 fake를 사용하고, 마지막 단계에서만 제한된 end-to-end 검증을 한다.
