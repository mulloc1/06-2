# 기준 10 · 파라미터 옵션화

> **평가 항목:** 항목 2 · 설계·구조 설명 — 파라미터 옵션화  
> **질문:** API 파라미터를 옵션화한 이유(재현성·실험·CLI 활용)를 설명할 수 있는가?

---

## 결론

**예.** `model` / `temperature` / `max_tokens`를 CLI 플래그로 노출한 이유는 **재현성**, **품질 실험**, **코드 변경 없는 운영 튜닝**이다. 기본값은 커밋/PR에 맞게 보수적으로 두고, 필요 시만 덮어쓴다.

---

## 옵션화 이유

### 1. 재현성

같은 diff라도 temperature가 높으면 출력이 매번 달라진다. 리뷰·데모·버그 재현 시에는 예를 들어 `--temperature 0`으로 맞춰 **비슷한 초안**을 다시 받을 수 있다. 모델명도 `--model`로 고정하면 “그때 쓰던 모델”을 문서에 남기기 쉽다.

### 2. 실험

커밋 제목은 짧고 사실 위주, PR How to Test는 더 긴 설명이 필요할 수 있다. `--max-tokens`를 서브커맨드 기본(400/700)과 다르게 주면, 코드 수정 없이 “얼마나 길어야 잘리는지”를 바로 비교할 수 있다.

### 3. CLI 활용

과제 요구사항(subject §4.2)이 CLI 옵션으로 파라미터를 바꾸라고 명시한다. 실무에서도 CI·스크립트에서 환경마다 다른 기본값을 넘기기 쉽다.

```bash
# 문서/스크립트에 재현 가능한 한 줄
python -m ai_gitgen commit --model gpt-4o-mini --temperature 0.2 --max-tokens 400
```

### 기본값 선택

| 파라미터 | 기본 | 근거 |
|----------|------|------|
| temperature | `0.2` | 커밋/PR은 창의성보다 일관성 |
| max_tokens (commit) | `400` | Subject + 짧은 Body |
| max_tokens (pr) | `700` | 세 섹션 불릿 |

하드코딩만 있으면 실험할 때마다 소스를 고쳐야 하고, 옵션만 있고 기본값이 없으면 매번 긴 인자가 필요하다. **합리적 기본 + 덮어쓰기**가 목표다.

---

## 한 줄 요약

옵션화는 **같은 도구로 재현·실험·운영 튜닝**을 코드 수정 없이 하기 위함이다.
