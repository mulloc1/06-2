# 기준 15 · 재생성 vs 후처리

> **평가 항목:** 항목 3 · 핵심 개념 이해 — 재생성 vs 후처리  
> **질문:** 출력 품질 문제 시 재생성과 후처리 중 어떤 전략을 택할지, 그 근거를 설명할 수 있는가?

---

## 결론

**이 프로젝트의 선택: 후처리 우선, 재생성은 최대 1회.** 길이·섹션 같은 **형식 문제**는 코드로 고치고, 섹션 전체가 비는 등 **의미·구조 결손**만 더 엄격한 프롬프트로 한 번 더 생성한다. (`docs/plan.md` Locked Decision)

---

## 두 전략 비교

| | **후처리 (post-process)** | **재생성 (re-generation)** |
|--|---------------------------|----------------------------|
| **무엇** | 받은 텍스트를 truncate·파싱·헤더 보완 | 같은(또는 강화된) 프롬프트로 API 재호출 |
| **정확도** | 형식은 확실, 의미 오류는 못 고침 | 의미·문장 품질 개선 가능, 비결정적 |
| **제어성** | 규칙이 코드에 있어 테스트·예측 가능 | temperature·모델에 의존 |
| **효율** | API 비용 0 | 토큰·지연·비용 추가 |

### 언제 후처리만으로 충분한가

- Subject가 72자를 살짝 넘음 → 잘라내거나 말줄임.
- 불릿이 4개 → 상위 3개만 유지.
- 구분선·헤더만 정리하면 되는 경우.

### 언제 재생성이 나은가

- `## How to Test` 블록 자체가 없음.
- Title만 있고 본문이 비어 있음.
- 후처리로 “없는 섹션”을 채워 넣으면 **가짜 내용**이 됨 → 재생성 쪽이 안전.

---

## 가이드라인 (이 CLI)

```
1) AI 1회 호출
2) polish로 형식 검사·가능한 수정
3) 고칠 수 없으면 needs_retry → 더 엄격한 제약으로 1회만 재호출
4) 그래도 실패하면 최선을 다한 텍스트 + (권장) 사용자 검토 안내
```

무제한 재생성은 비용·대기·비결정성을 키우므로 **1회 캡**이 있다. “창의적으로 다시 써 줘”가 아니라 “형식 미달일 때만 구조 복구”가 목적이다.

현재 `polish.py`는 스텁이므로 런타임은 사실상 **프롬프트 유도만** 사용한다. 위 전략은 설계·평가용 답변의 근거다.

---

## 한 줄 요약

형식은 **후처리로 제어**, 구조 결손은 **제한된 재생성** — 비용·제어성·정확도의 절충이다.
